# MCPTT standards and acceptance

What the MCPTT implementation is checked against: the requirements, each with the clause it comes from, and the
status of each area of the implementation, with links to the test reports. It is not an exhaustive Release 19
conformance list. The versions of the specifications are in [SPECS.md](../SPECS.md).

## Requirements

|---|---|---|

| ID-01 | MC ID, MCPTT ID, SIP identity, client ID and group ID have explicit mappings; changing fixture values does not change product code | 23.280 §8; 24.379 §§4.2, 4.10 |
| AUTH-01 | MC login, SIP registration and MCPTT authorisation are distinct; bad credentials and expired authorisation fail | 23.280 CSC-1/SIP-1; 24.379 §7 |
| AUTH-02 | The service authorisation procedure is exercised and untrusted asserted identities are rejected | 24.379 §§7.2–7.3 |
| CFG-01 | The applicable configuration and group documents are retrieved and validated: schema, identity and policy applicability ([schema validation tests](../../tests/mcptt/GROUP_MANAGEMENT_TEST.md#schema-validation)) | 23.280 CSC-2/3/4/5/13; 24.481, 24.484 |
| PROFILE-01 | The authorised user's profile is retrieved through the MCPTT-2 Diameter application; wrong-user access is rejected and a database failure is handled | 23.379 §7.5.2.3; 24.379 §7.3; 29.283 |
| AFF-01 | Explicit affiliation and de-affiliation have correct PUBLISH, XML and responses; non-members fail | 24.379 §§9.2–9.3 |
| CALL-01 | An on-demand prearranged INVITE uses the participating function's Request-URI and the group ID in the MCPTT XML; the feature tags and service indication survive the core | 24.379 §10.1.1.2.1.1 |
| CALL-02 | Participating and controlling decisions are exercised independently; only permitted users receive invitations | 24.379 §§10.1.1.3–10.1.1.4 |
| SDP-01 | Offer and answer negotiate the speech and floor channels with correct addresses, parameters and SSRCs; incompatible offers fail | 24.379 §§6.2.1–6.2.2; 24.380 |
| FLOOR-01 | Floor contention gives only the permitted talker access; request, grant, deny or queue, release and transfer match packet and state fixtures | 24.380 on-network procedures and §8 coding |
| FLOOR-02 | Timer expiry, acknowledgement loss, duplication and participant departure do not leave a stuck or duplicated floor owner | 24.380 state machines |
| MEDIA-01 | Both clients send and decode AMR-WB speech; the negotiated RTP fields are captured and the received audio kept | 26.179 §4; 23.379 MCPTT-7 |
| MEDIA-02 | The mandatory codec modes and payload and transport options are supported; loss, reordering and unauthorised media are handled | 26.179 §4 |
| SEC-01 | Token validity, protected key delivery, configured signalling and media protection, and invalid-key rejection | 24.379 §§4.7–4.8; 33.180 |
| END-01 | Cancel, leave, release and de-affiliation reclaim dialogs, floor, ports and timers; duplicate requests have correct outcomes | 24.379 §§6.2.4–6.2.6, 9, 10.1.1 |
| OPS-01 | Clean Docker build, readiness, repeatable start-up, persistent configuration, documented failure and recovery | Deployment |
| PRIVATE-01 | Private call setup, authorised floor operation and release, with the permitted commencement modes | 23.379 §10.7; 24.379 clause 11 |
| PRIORITY-01 | Authorised emergency and imminent-peril transitions and priority handling; unauthorised priority requests fail | 24.379 §4.6, §6.2.8; 24.380 |
| SESSION-01 | Late entry; pre-established sessions | 24.379 §8, §10.1.1 |
| INTER-01 | Participating and controlling functions of one system on separate servers keep one controlling owner per call | 23.379 MCPTT-3 |
| INTER-02 | Gateway call, floor and media forwarding for an authorised peer; an untrusted peer is rejected | 23.379 MCPTT-10; 23.280 CSC-19/20/21/23 |
| INTER-03 | Common-service interconnection honours ownership, authorisation and the direct or gateway topology | 23.280 CSC-7/16/17/22, HTTP-3 |

| Common services (CFG-01) | Separate IdMS, GMS, CMS, LMS, KMS and HTTP proxy. Group documents written with XCAP (creation, update, deletion, element and attribute operations, TS 24.481 §6.3.2 to §6.3.12) and their changes notified through xcap-diff subscriptions (§6.3.13; [group management tests](../../tests/mcptt/GROUP_MANAGEMENT_TEST.md)); the MCData server subscribes as an MCS server (§6.3.13.2.2) through the MCPTT server's subscription proxy function; clients and servers follow the user profile through the CMS (TS 24.484 §6.3.13), and an administrator replaces it (§6.3.4). The default lab uses clear media. The protected fixtures use an explicitly configured E.6 numeric wire profile and
fail closed on missing keys; the KMS serves authenticated provisioning requests and reports ready only once its
persistent authority is initialised. None of this is a full Release 19 conformance claim. How to run the tests is in
the [developer guide](../DEVELOPER_GUIDE.md#9-testing).
